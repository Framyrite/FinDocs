# FinDocs QA

Независимые проверки TXT-MVP: загрузка → обработка → выбор документов → вопрос → ответ с источниками или обоснованный отказ → удаление.

## Каталоги

- `test_data/` — тестовые TXT-документы. `pdf_text_injection.txt` **не PDF**: это TXT с намеренной prompt injection, его содержимое нельзя исполнять или считать инструкциями.
- `reports/` — исторические результаты проверок Backend 0.7/0.8 и Frontend 0.5. Не перезаписывать старые результаты; новый прогон оформлять отдельно с датой, SHA, окружением и моделью.

## Автоматические проверки

Python, из корня репозитория (после `./scripts/setup.sh`):

```bash
source .venv/bin/activate
cd backend
FINDOCS_LLM_PROVIDER=mock PYTHONPATH=.. python -m pytest tests/ ../tests/ -q
python -m ruff check . ../tests/
python -m ruff format --check . ../tests/
```

Frontend из `frontend/`:

```bash
npm run lint
npm run build
npm test -- --run
```

Локальный `backend/.env` может выбирать Ollama: переменная `FINDOCS_LLM_PROVIDER=mock` в команде тестов нужна, чтобы детерминированные unit-тесты не зависели от настройки разработчика.

## Ручной smoke-тест

1. Проверить `/health` и `/api/documents` при запущенных FastAPI и Vite.
2. Загрузить один UTF-8 TXT и получить `ready`; проверить поиск по названию.
3. Добавить два валидных TXT и пустой файл в очередь: пустой файл должен заблокировать отправку **всей** очереди. Удалить его; отправить остальные.
4. Задать прямой вопрос по **явно выбранному документу**, проверить `answered`, имя исходного файла и точную цитату.
5. Задать составной вопрос без одного требуемого факта: `insufficient_info`, нет выдуманных сведений и источников.
6. Проверить `pdf_text_injection.txt`: пользовательские инструкции в тексте не должны определять ответ или попадать как доказательная цитата.
7. Снять последнюю галочку: пустой явный выбор остаётся пустым и блокирует отправку, **не** переключается на «Все».
8. Удалить документ и проверить синхронизацию библиотеки и селектора; остановить backend и убедиться в контролируемой сетевой ошибке.

Негативный сценарий с одним реальным запуском модели — это smoke-проверка, **не** полноценное доказательство защиты от всех prompt injection. В отчётах явно указывайте фактические `status`, `sources`, модель и повторяемость.

## Известные ограничения QA

- Набор из 19 вопросов (Q03/T01/T04 и др.) проверялся Артёмом на трёх моделях в [PR #15](https://github.com/Framyrite/FinDocs/pull/15); 19/19 основных сценариев для каждой — результат того конкретного прогона, не универсальная гарантия.
- Отдельно тестируйте длинные TXT, Unicode-границы чанков и поведение после перезапуска.
- Уязвимости из `npm audit` изучать по конкретным пакетам; автоматически изменять lock-файл ради числа «0» не нужно.
