# Backend 0.8.3 — предложение по контексту и цитированию (черновик)

**Статус:** предлагается к согласованию Владиславом Логиновым. Этот файл не заменяет действующий `mvp-contracts.md` v0.2 §6.7.

## Мотивировка

По результатам прогона 12 QA-вопросов на Qwen3.5 4B после полного контекста: `D01`, `D03`, `D04`, `P01`, `P02`, `P03` получили `answered`, `D02` — `insufficient_info`, пять негативных сценариев — `insufficient_info`. При этом `Source.quote` часто цитировал вводные предложения, а не доказательства; `D03` не ответил на часть «кем».

## Предлагаемое поведение

1. **Лексический поиск:** узнавать латинские аббревиатуры в верхнем регистре длиной 2–5 букв с одиночной цифровой сноской `[1-9]` (например, `FIFO1` → `fifo`); числовую сноску не удалять из исходного TXT или из `Source.quote`. Правила для остальных слов прежние.
2. **LLM-контекст:** брать только валидированные ранжированные чанки; для вопросов на объяснение причины допускать ближайший следующий или предыдущий сохранённый чанк **того же блока и документа**, если он содержит хотя бы один термин вопроса. Сначала включаются найденные чанки, затем соседи в оставшиеся слоты; не более `TOP_K=3` контекстных чанков всего. При невалидных координатах сосед не используется. Убирать повторяющиеся символьные пересечения; лимит первого среза — 6000 **символов** (не точный бюджет токенов). Пропущенные из-за лимита чанки не становятся источниками LLM.
3. **Ответ реальной LLM:** после генерации выбирать цитаты с учётом вопроса и ответа. Совпадение по лексике — средство ранжирования, **не доказательство семантической полноты/истинности**. Предпочитать короткие выдержки с содержательными словами ответа, а не только с формулировкой вопроса.
4. **Происхождение:** цитата — дословный непрерывный срез *только того диапазона сохранённого чанка, который был фактически включён в prompt*. Поля `document_id`, `block_id`, `chunk_id`, `start_char`, `end_char` вычислять из исходного `DocumentBlock`; `quote == original_text[start_char:end_char]`; длина не более 300 Unicode-символов; не более `TOP_K=3` источников. Не показывать повторяющиеся/сильно перекрытые диапазоны.
5. **MockLLM:** без изменений. Для `MockLLM` по-прежнему применять `build_sources` из §6.7 и возвращать ответ `[MOCK]` исключительно из тех же цитат.
6. **Ошибки/отказы:** сохранить текущий HTTP/API-контракт, 503 при техническом сбое, `insufficient_info` при недостатке данных, отказ от частичных ответов по существенным частям вопроса. Подтверждение полноты остаётся отдельной задачей, если self-check Qwen не справляется.

## Критерии проверки

- `D02` должен находить фрагмент про FCFS/FIFO, включая написание `FIFO1`, и не выдавать ответ из одного SJF/RR.
- `D01`, `D04`, `P01` должны получать релевантные объясняющие цитаты, а `P02` — цитаты про реальные различия FCFS/RR. Для `D04` объяснение невозможности заранее узнать продолжительность `CPU burst` должно реально присутствовать в переданном контексте, а не возникать из общих знаний модели.
- `D03` требует отдельной оценки полноты «год **и кем**»; частичный ответ недопустимо считать Pass.
- N01–N03 и I01–I02 остаются `insufficient_info`; отдельный прямой тест prompt injection должен **реально передать** инструкцию в модель.
- Все unit/integration тесты, Ruff, проверка Unicode-смещений, лимитов, области выбранных документов; повторный QA через локальную Ollama и анализ цитат до коммита 0.8.3.

**Ограничения:** ни новая модель, ни embeddings/vector DB, ни изменения Ollama `SYSTEM_PROMPT`, ни новый API не входят в этот патч. Перед merge предложения выше требуется точное оформление и согласование поправки к нормативной части §6.7.
