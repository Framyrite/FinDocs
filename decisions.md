# Журнал архитектурных решений FinDocs

## Для чего нужен этот файл

`decisions.md` — это краткий журнал важных технических и архитектурных решений проекта.

Он нужен, чтобы команда понимала:

- какие решения были приняты;
- почему мы выбрали именно такой вариант;
- что изменилось со временем;
- какие решения считаются актуальными;
- почему сейчас не стоит возвращаться к уже обсуждённым вариантам без новых оснований.

Это **не документация всей архитектуры**.  
Текущее устройство системы описывается в `architecture.md`, а причины ключевых решений и история их изменения — здесь.

---

## Легенда

### Нумерация решений

Каждое решение получает уникальный номер:

`ADR-001`, `ADR-002`, `ADR-003` ...

Номер после создания не меняется и не переиспользуется.

### Статусы

Используем минимальный набор:

- **Принято** — решение действует сейчас.
- **Изменено** — решение было пересмотрено и заменено другим.
- **Отменено** — решение больше не применяется.
- **На обсуждении** — решение ещё не принято.

### Версии

Отдельные версии для каждого ADR не нужны.

Версия фиксируется на уровне самого файла через историю Git.

Если решение меняется существенно, не переписываем историю молча:
1. меняем статус старого решения на `Изменено`;
2. указываем, каким решением оно заменено;
3. создаём новый ADR с новым номером.

### Как отмечать изменения

Для небольших правок внутри решения достаточно обычного коммита Git.

Если меняется **само архитектурное решение**, запись не переписываем задним числом. Вместо этого добавляем новый ADR.

Пример:

```text
ADR-003 — PostgreSQL + pgvector
Статус: Изменено
Заменено: ADR-008
```

А в новом решении:

```text
ADR-008 — Другое решение для хранения векторов
Статус: Принято
Заменяет: ADR-003
```

## ADR-002 — Макеты основного пользовательского сценария

**Статус:** Принято

## Контекст
Необходимо было определить основной пользовательский путь FinDocs и структуру рабочего экрана.

## Решение
В качестве основного сценария принят путь:
загрузка документа → обработка → вопрос → ответ → проверка источника.
Интерфейс строится вокруг библиотеки документов, рабочей области вопроса и области просмотра источника.

## Почему
Такой вариант позволяет выполнить основной сценарий без лишних переходов и сразу показать связь ответа с исходным материалом.
Последствия
Макеты и дальнейшая реализация интерфейса должны поддерживать единый пользовательский сценарий и работу с источниками.

## Связанные решения
ADR-004 — Состояния интерфейса.

## ADR-003 — Подход к выбору локальной LLM

**Статус:** На обсуждении

## Контекст
Для FinDocs необходимо выбрать локальную языковую модель, подходящую для работы с русскоязычными учебными материалами и RAG.

## Решение
Модель не фиксируется до практического сравнения кандидатов. При выборе учитываются русский язык, работа по переданному контексту, отказ при недостатке информации, требования к ресурсам и удобство интеграции с Python / FastAPI.

## Почему
Теоретических характеристик недостаточно для выбора модели для конкретного сценария FinDocs.
Последствия
Backend не должен зависеть от конкретной модели. Для интеграции используется отдельный LLM-адаптер.

## Связанные решения
ADR-005 — Базовая структура backend.

## ADR-004 — Состояния основного интерфейса

**Статус:** Принято

## Контекст
Необходимо было явно определить состояния документов и ответов в основном пользовательском сценарии.

## Решение
Для документов используются состояния загрузки, обработки, готовности, предупреждения и ошибки.
Для ответов различаются ожидание, полный ответ, частичный ответ, недостаток информации и техническая ошибка.
Также отдельно отображается область поиска: все готовые документы или выбранные материалы.

## Почему
Разные ситуации требуют разного поведения интерфейса и не должны смешиваться между собой.
Последствия
Frontend и backend должны использовать согласованные состояния. Недостаток информации не должен отображаться как техническая ошибка.

## Связанные решения
ADR-002 — Макеты основного пользовательского сценария.

## ADR-005 — Базовая структура backend FinDocs

**Статус:** Принято

## Контекст
Требовалась расширяемая основа backend до подключения полноценного RAG и конкретной LLM.
Решение
Backend реализуется на Python + FastAPI как модульный монолит с разделением API, документов, RAG, LLM и слоя хранения.
На текущем этапе добавляются /health, конфигурация через переменные окружения и общий LLMAdapter с mock-реализацией.

## Почему
Такой вариант позволяет подготовить основу проекта без привязки к ещё не выбранной модели и не смешивать разные зоны ответственности.

## Последствия
Полный RAG, PostgreSQL + pgvector, обработка форматов и реальная LLM подключаются на следующих этапах.

## Связанные решения
ADR-003 — Подход к выбору локальной LLM.

## ADR-006 — Подход к QA и проверке RAG

**Статус:** Принято

## Контекст
Необходимо было подготовить основу для объективной проверки качества первого RAG-прототипа.
Решение
Тестирование разделяется на два уровня:
Retrieval — найден ли правильный фрагмент;
Generation — корректно ли модель использовала найденный контекст.
Дополнительно фиксируются тестовые документы, контрольные вопросы, источники и негативные сценарии.

## Почему
Разделение позволяет определить, проблема возникла при поиске информации или при формировании ответа.

## Последствия
Результаты Retrieval и Generation оцениваются отдельно, а RAG-эксперименты проводятся на одном и том же наборе вопросов.

## Связанные решения
ADR-002 — Макеты основного пользовательского сценария.

---

## ADR-007 — Проверка покрытия требований MVP

**Статус:** Принято

## Контекст
До дальнейшей реализации необходимо было проверить согласованность требований MVP с архитектурой, интерфейсом и QA-материалами.

## Решение
Для каждого требования фиксируется статус:
Покрыто / Частично / Не покрыто / Требует уточнения / Вне MVP.
Противоречия и неподтверждённые архитектурные предположения не исправляются молча, а выносятся на согласование.

## Почему
Это позволяет не добавлять в MVP неподтверждённые функции и видеть пробелы в проверке важных требований.

## Последствия
Требования, архитектура, UX и QA должны использовать согласованные формулировки и одинаковые границы MVP.

## Связанные решения
ADR-002 — Макеты основного пользовательского сценария.
ADR-004 — Состояния основного интерфейса.
ADR-006 — Подход к QA и проверке RAG.

ADR-008 — Первый технический вертикальный срез TXT

Статус: Принято

Контекст

Необходимо было определить границы первого рабочего сценария FinDocs, не включая сразу все планируемые форматы и компоненты системы.

Решение

Первый технический вертикальный срез ограничивается обработкой TXT: загрузка документа, декодирование, разбиение на блоки и чанки, получение ответа с источниками через демонстрационный поиск.

Другие форматы, OCR, PostgreSQL, embeddings и реальная LLM в этот срез не входят.

Почему

Ограниченный сценарий позволяет проверить основные технические компоненты и их взаимодействие до расширения системы.

Последствия

Дальнейшая разработка ведётся поэтапно. Первый технический срез не считается полноценным RAG-MVP.

Связанные решения

ADR-005 — Базовая структура backend FinDocs.

ADR-009 — Токенизатор и правила разбиения текста

Статус: Принято

Контекст

Необходимо было исключить различия в результатах разбиения одного документа на разных машинах и обеспечить совместимость с будущим этапом embeddings.

Решение

Для токенизации используется intfloat/multilingual-e5-small с закреплённой версией tokenizers, ревизией модели и SHA-256 файла токенизатора.

Размер чанка — 350 токенов, перекрытие — 50 токенов.

Символьные диапазоны определяются по offsets токенизатора. Содержимое чанка должно точно соответствовать диапазону исходного блока без изменения текста.

Почему

Единый токенизатор и фиксированный алгоритм обеспечивают воспроизводимость обработки документов.

Последствия

Токенизатор должен быть доступен локально. Изменение его версии или правил чанкинга требует проверки эталонных результатов и тестов.

Связанные решения

ADR-005 — Базовая структура backend FinDocs.

ADR-010 — Детерминированные идентификаторы и источники

Статус: Принято

Контекст

Необходимо обеспечить стабильную связь между исходным документом, блоками, чанками и источниками ответов.

Решение

Для блоков и чанков используется UUID5 на основе ID документа и позиции элемента.

Для текстовых диапазонов используется единая система координат: символы Unicode в Python, начало включается, конец не включается.

Источник ответа должен ссылаться на реально найденный чанк и содержать точную цитату из исходного документа.

Почему

Стабильные идентификаторы упрощают тестирование и позволяют однозначно восстановить происхождение найденного фрагмента.

Последствия

Повторная обработка одного документа с одинаковыми параметрами даёт те же идентификаторы. Выдуманные источники и изменённые цитаты недопустимы.

Связанные решения

ADR-006 — Подход к QA и проверке RAG.

ADR-011 — Локальное файловое хранение документов

Статус: Принято

Контекст

Для первого TXT-среза требовалось определить способ хранения документов и результатов обработки без подключения PostgreSQL.

Решение

Используется локальное файловое хранилище за интерфейсом DocumentRepository.

Для каждого документа создаётся отдельный каталог с файлами original.bin, meta.json и result.json.

Корневой каталог задаётся через FINDOCS_DATA_DIR, по умолчанию — backend/data/.

Запись файлов выполняется атомарно через временный файл и переименование.

Почему

Файлового хранения достаточно для первого среза. Интерфейс репозитория позволяет впоследствии заменить реализацию без изменения API-контракта.

Последствия

Документы сохраняются между перезапусками приложения. PostgreSQL и pgvector подключаются на следующих этапах.

Связанные решения

ADR-005 — Базовая структура backend FinDocs.

ADR-012 — Жизненный цикл и фоновая обработка документов

Статус: Принято

Контекст

Загрузка и обработка документов могут занимать время, поэтому необходимо разделить принятие файла и завершение его обработки.

Решение

Используются статусы uploaded, processing, ready и error.

Фоновая обработка выполняется через FastAPI BackgroundTasks с вызовом существующего process_txt().

При запуске приложения незавершённые документы переводятся в error. Удалённый документ не должен восстанавливаться после завершения фоновой обработки.

Для MVP используется один процесс uvicorn и внутрипроцессная блокировка.

Почему

Такой подход позволяет обрабатывать документы в фоне, сохранять результаты и корректно обрабатывать удаление и перезапуск приложения без внешней очереди задач.

Последствия

Система не поддерживает несколько worker-процессов и не использует Celery или Redis на текущем этапе.

Связанные решения

ADR-008 — Первый технический вертикальный срез TXT.

ADR-013 — Демонстрационный поиск без RAG

Статус: Принято

Контекст

Требовалось обеспечить проверку сценария вопросов по документам до подключения embeddings, векторного поиска и реальной LLM.

Решение

Используется лексический поиск LexicalRetriever и MockLLM.

Релевантность определяется совпадением нормализованных основ слов. Минимальное покрытие — 0.6, максимальное количество найденных чанков — 3.

Ответы формируются на основе найденных фрагментов. Источники создаются только для реально найденных чанков.

Почему

Демонстрационная реализация позволяет проверить API, поиск и передачу источников без зависимости от настоящей модели.

Последствия

Результат демонстрационного поиска не считается полноценным ответом RAG. Статус partial на этом этапе не используется. При отсутствии достаточных совпадений возвращается insufficient_info.

Связанные решения

ADR-006 — Подход к QA и проверке RAG.
