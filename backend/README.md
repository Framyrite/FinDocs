
# FinDocs Backend

Серверная часть FinDocs на Python 3.12 и FastAPI.

**Backend 0.6** реализует локальную библиотеку TXT-документов и демонстрационный поиск по их содержимому с ответами на вопросы и точными цитатами из источников.

В проекте используются файловое хранилище, детерминированный лексический поиск и `MockLLM`. Настоящая LLM, embeddings и векторная база данных пока не подключены.

## Реализованные компоненты

### Библиотека документов — Backend 0.5

- `GET /health` — проверка доступности приложения.
- `POST /documents` — загрузка TXT-файла.
- `GET /documents` — список документов с фильтрацией.
- `GET /documents/{document_id}` — информация о документе и его статусе.
- `DELETE /documents/{document_id}` — удаление документа.
- `app/documents/` — модели, файловое хранилище и управление обработкой.
- `app/processing/` — декодирование TXT, создание блоков и чанков.

### Поиск и вопросы — Backend 0.6

- `POST /chat/ask` — ответ на вопрос по готовым документам.
- `app/chat/models.py` — модели HTTP-запроса, ответа и источников.
- `app/chat/service.py` — выбор документов и координация ответа.
- `app/chat/sources.py` — формирование точных цитат.
- `app/retrieval/lexical.py` — детерминированный лексический поиск.
- `app/llm/adapter.py` — интерфейс LLM-адаптера.
- `app/llm/mock.py` — демонстрационное формирование ответа без настоящей LLM.

Поддерживаются TXT-файлы в кодировке UTF-8, включая UTF-8 BOM.

## Требования

- Python 3.12.
- Доступ к PyPI при первоначальной установке зависимостей.
- Локальный токенизатор `multilingual-e5-small`.
- Один процесс Uvicorn для работы с файловым хранилищем.

PostgreSQL, pgvector, Ollama, PDF, DOCX и настоящая LLM не требуются для запуска Backend 0.6.

Не перезаписывайте существующий `.env`, если в нём уже есть локальные настройки.

| --- | --- | --- |

Приоритет конфигурации:

1. Переменные окружения процесса.
2. Файл `backend/.env`.
3. Значения по умолчанию.

После изменения настроек сервер необходимо перезапустить.

## Установка токенизатора

TXT-обработка использует токенизатор `multilingual-e5-small`.

Файл `tokenizer.json` не хранится в Git и не загружается автоматически при запуске приложения.

Из каталога `backend`:

```bash
mkdir -p models/multilingual-e5-small

curl -fL --retry 3 \
  "https://huggingface.co/intfloat/multilingual-e5-small/resolve/ada7b62be30f82b0bc5da131b0477721c8fc14e9/tokenizer.json" \
  -o models/multilingual-e5-small/tokenizer.json
```

Проверка SHA-256 на Linux / macOS:

```bash
echo "0b44a9d7b51c3c62626640cda0e2c2f70fdacdc25bbbd68038369d14ebdf4c39  models/multilingual-e5-small/tokenizer.json" \
  | shasum -a 256 -c -
```

Ожидаемый результат:

```text
models/multilingual-e5-small/tokenizer.json: OK
```

Используется `tokenizers==0.23.3`.

Токенизатор нужен при обработке новых TXT-файлов. Лексический поиск Backend 0.6 работает с уже сохранёнными чанками.

## Локальное хранение документов

Документы сохраняются на диске в каталоге, указанном через `FINDOCS_DATA_DIR`.

Структура по умолчанию:

```text
backend/
└── data/
    └── documents/
        └── <uuid>/
            ├── original.bin
            ├── meta.json
            └── result.json
```

Назначение файлов:

- `original.bin` — исходные байты TXT без изменений.
- `meta.json` — метаданные и текущий статус документа.
- `result.json` — результат успешной обработки: блоки и чанки.

`result.json` появляется после успешной обработки.

Каждый документ идентифицируется UUID. Одинаковые имена файлов разрешены.

Для сохранения файлов используются атомарные операции записи.

Каталог `backend/data/` исключён из Git.

### Состояния документов

| Статус | Значение |
| --- | --- |
| `uploaded` | Файл принят и сохранён |
| `processing` | Выполняется TXT-обработка |
| `ready` | Обработка успешна, результат доступен |
| `error` | Обработка завершилась ошибкой или результат недоступен |

Основные переходы:

```text
uploaded → processing → ready
                      ↘ error

ready → error (при повреждении или отсутствии результата)
```

У документа со статусом `error` заполнены `error_code` и `error_message`.

У документа со статусом `ready` поля ошибки равны `null`.

### Проверка доступности результата

Статус `ready` означает, что обработка успешно завершена и сохранённый результат доступен.

Если у готового документа отсутствует или повреждён `result.json`, репозиторий переводит его в `error` с кодом `processing_failed`.

Проверка выполняется при чтении документа и восстановлении после перезапуска.

Исходный файл сохраняется. Повреждённый результат не удаляется автоматически, чтобы его можно было исследовать.

Повреждённый `meta.json` делает документ недоступным через API, но каталог сохраняется. Такой каталог продолжает учитываться в лимите документов.

## HTTP API документов — Backend 0.5

### POST /documents — загрузка TXT

Эндпоинт принимает `multipart/form-data` с полем `file`.

Для ручной проверки создайте файл:

```bash
printf 'Привет, FinDocs!\n' > example.txt
```

Загрузите:

```bash
curl -i \
  -F "file=@example.txt;type=text/plain" \
  http://127.0.0.1:8000/documents
```

Успешный ответ — HTTP `202 Accepted`.

Пример структуры ответа:

```json
{
  "id": "12345678-1234-5678-1234-567812345678",
  "filename": "example.txt",
  "format": "txt",
  "status": "uploaded",
  "error_code": null,
  "error_message": null,
  "size_bytes": 17,
  "created_at": "2026-11-05T12:00:00Z"
}
```

UUID и дата приведены для иллюстрации. Реальные значения определяются сервером.

После сохранения документа запускается фоновая задача FastAPI `BackgroundTasks`.

Фоновая задача:

1. Получает UUID документа.
2. Читает сохранённый `original.bin`.
3. Вызывает `process_txt()`.
4. Сохраняет блоки и чанки в `result.json`.
5. Переводит документ в `ready` либо `error`.

Неверная UTF-8 кодировка и TXT из одних пробелов могут пройти первоначальную HTTP-загрузку, но затем получить статус `error`.

### GET /documents — список документов

```bash
curl http://127.0.0.1:8000/documents
```

Формат ответа:

```json
{
  "items": [],
  "total": 0
}
```

`items` содержит документы, `total` — количество элементов после фильтрации.

Документы сортируются по времени создания: новые первыми.

Доступны необязательные параметры:

- `status` — `uploaded`, `processing`, `ready` или `error`.
- `q` — подстрока имени файла без учёта регистра.

Пример:

```bash
curl "http://127.0.0.1:8000/documents?status=ready&q=example"
```

Постраничная выдача не реализована.

### GET /documents/{document_id} — получение документа

```bash
curl http://127.0.0.1:8000/documents/12345678-1234-5678-1234-567812345678
```

Успешный ответ — HTTP `200 OK` с актуальными метаданными.

Если документ не найден, возвращается HTTP `404` с кодом `document_not_found`.

Маршрут можно использовать для polling: frontend периодически проверяет статус, пока документ не перейдёт в `ready` или `error`.

### DELETE /documents/{document_id} — удаление

```bash
curl -i -X DELETE \
  http://127.0.0.1:8000/documents/12345678-1234-5678-1234-567812345678
```

Успешный ответ — HTTP `204 No Content` без тела.

При удалении физически удаляется каталог документа со всеми файлами.

После удаления документ:

- не появляется в `GET /documents`;
- не доступен через `GET /documents/{document_id}`;
- не участвует в поиске `POST /chat/ask`;
- не восстанавливается после завершения ранее запущенной фоновой обработки.

Повторное удаление возвращает `404 document_not_found`.

### Ограничения загрузки

По умолчанию:

- Максимальный размер TXT — 10 МиБ.
- Максимальное количество документов — 100.
- Нулевой файл запрещён.
- Поддерживаются только TXT-файлы.

При загрузке используется ограниченное чтение:

```python
file.read(max_bytes + 1)
```

При стандартном лимите приложение читает не более 10 МиБ + 1 байт содержимого файла в обработчике. Дополнительный байт позволяет определить превышение лимита.

FastAPI/Starlette может временно сохранять multipart-загрузки на диск ещё до выполнения обработчика. Поэтому такая проверка не ограничивает весь входящий HTTP-запрос.

Для публичного развёртывания необходим дополнительный лимит HTTP-запроса на уровне сервера или reverse proxy.

Отклонённый файл не создаёт документ в библиотеке.

### Ошибки API документов

| HTTP | Код | Описание |
| --- | --- | --- |
| 415 | `unsupported_format` | Неподдерживаемый формат |
| 413 | `file_too_large` | Превышен лимит размера |
| 422 | `empty_file` | Файл нулевого размера |
| 409 | `document_limit_reached` | Достигнут лимит документов |
| 404 | `document_not_found` | Документ не найден |
| 422 | `validation_error` | Некорректный UUID, статус или структура HTTP-запроса |

Формат ошибок:

```json
{
  "error": {
    "code": "file_too_large",
    "message": "Файл больше допустимого размера (10 МБ).",
    "details": {
      "max_size_mb": 10
    }
  }
}
```

Поля `code` и `message` обязательны. Поле `details` необязательное.

### Ошибки фоновой обработки

Уже загруженный документ не получает HTTP-ошибку задним числом.

Вместо этого обновляются `status`, `error_code` и `error_message`.

| Код | Причина |
| --- | --- |
| `invalid_encoding` | TXT не декодируется как UTF-8 |
| `empty_document` | После декодирования отсутствует содержательный текст |
| `processing_failed` | Другая ошибка обработки, прерванная обработка или недоступный результат |

## HTTP API вопросов — Backend 0.6

### POST /chat/ask

Эндпоинт выполняет детерминированный лексический поиск по сохранённым чанкам готовых TXT-документов.

Для генерации демонстрационного ответа используется `MockLLM`.

Embeddings, внешние API и настоящая LLM не используются.

### Запрос

Пример:

```bash
curl -X POST http://127.0.0.1:8000/chat/ask \
  -H "Content-Type: application/json" \
  -d '{
    "question": "облигация доход",
    "document_ids": null
  }'
```

Тело запроса:

```json
{
  "question": "облигация доход",
  "document_ids": null
}
```

Поля:

| Поле | Тип | Правила |
| --- | --- | --- |
| `question` | `string` | От 1 до 2000 символов после удаления крайних пробелов |
| `document_ids` | `UUID[] \| null` | Необязательная область поиска |

Поведение `document_ids`:

- Отсутствует или `null` — поиск по всем готовым документам.
- Непустой список UUID — поиск только по указанным документам.
- `[]` — ошибка валидации.
- Повторяющиеся UUID обрабатываются один раз.
- Несуществующий UUID — `404 document_not_found`.
- Документ не в состоянии `ready` — `409 document_not_ready`.

Если поиск по всем готовым документам невозможен, потому что таких документов нет, возвращается `409 no_ready_documents`.

При выборе документов обработка TXT не запускается повторно: используются ранее сохранённые результаты.

### Успешный ответ

При наличии подходящих источников возвращается HTTP `200 OK`.

Пример структуры:

```json
{
  "status": "answered",
  "answer": "[MOCK] Найдены фрагменты по ключевым словам вопроса:\n1. «Облигация приносит доход.»",
  "sources": [
    {
      "document_id": "11111111-1111-4111-8111-111111111111",
      "filename": "Материал.txt",
      "block_id": "22222222-2222-4222-8222-222222222222",
      "chunk_id": "33333333-3333-4333-8333-333333333333",
      "start_char": 0,
      "end_char": 25,
      "quote": "Облигация приносит доход."
    }
  ]
}
```

UUID и координаты в примере иллюстративные. Реальный ответ содержит идентификаторы и диапазоны сохранённого документа.

Формат успешного ответа:

- `status` — `answered` или `insufficient_info`.
- `answer` — текст демонстрационного ответа.
- `sources` — массив подтверждающих источников.

В ответе может быть от 1 до 3 источников.

Демонстрационная реализация не использует статус `partial`.

### Точные цитаты и координаты

Каждый элемент `sources` содержит:

| Поле | Значение |
| --- | --- |
| `document_id` | UUID исходного документа |
| `filename` | Имя загруженного файла |
| `block_id` | UUID блока |
| `chunk_id` | UUID чанка |
| `start_char` | Начало цитаты в исходном TXT |
| `end_char` | Конец цитаты в исходном TXT, не включительно |
| `quote` | Точный текст цитаты |

Главный инвариант:

```python
source.quote == decoded_txt[source.start_char:source.end_char]
```

Координаты измеряются Unicode-символами Python-строки, а не байтами UTF-8.

Это важно для кириллицы, emoji и других многобайтовых символов.

UTF-8 BOM удаляется при декодировании через `utf-8-sig` и не учитывается в символьных координатах.

Координаты чанков хранятся относительно блока, поэтому при формировании абсолютного диапазона учитывается начальное смещение блока.

Цитаты выбираются из сохранённого текста без исправления орфографии, изменения регистра и переписывания предложений.

Максимальная длина цитаты — 300 символов.

Если предложение длиннее лимита, берётся окно из исходного текста вокруг первого найденного совпадения.

Полностью одинаковые диапазоны одного документа не дублируются в `sources`. Частично пересекающиеся диапазоны могут присутствовать.

### Недостаточно информации

Если готовые документы существуют, но поиск не нашёл подходящих фрагментов, возвращается HTTP `200 OK`:

```json
{
  "status": "insufficient_info",
  "answer": "В выбранных материалах не удалось найти достаточную информацию для ответа.",
  "sources": []
}
```

В этом случае `MockLLM` не вызывается.

Это не техническая ошибка. Ответ означает, что лексический алгоритм не нашёл достаточно совпадений в выбранных материалах.

### Ошибки API чата

| HTTP | Код | Причина |
| --- | --- | --- |
| 422 | `invalid_question` | Некорректный вопрос, UUID или список документов |
| 422 | `question_too_long` | Вопрос длиннее 2000 символов |
| 404 | `document_not_found` | Указанный документ отсутствует |
| 409 | `document_not_ready` | Указанный документ не готов |
| 409 | `no_ready_documents` | Нет готовых документов при общей области поиска |
| 503 | `llm_unavailable` | Технический сбой LLM-адаптера |
| 500 | `internal_error` | Неожиданная ошибка сервера |

Пример:

```json
{
  "error": {
    "code": "no_ready_documents",
    "message": "Нет готовых документов для поиска."
  }
}
```

Для `POST /chat/ask` используется отдельное отображение ошибок HTTP-валидации.

Существующий код `validation_error` для остальных маршрутов FastAPI сохраняется.

Технические ошибки не должны раскрывать внутренние пути файловой системы, трассировки исключений и другие детали реализации.

## Алгоритм лексического поиска

Реализация находится в:

```text
app/retrieval/lexical.py
```

Поиск выполняется по сохранённым чанкам документов со статусом `ready`.

Он детерминированный: одинаковые данные и вопрос приводят к одинаковому ранжированию.

### Нормализация

Для вопроса и содержимого чанков применяются одинаковые правила:

1. Перевод текста в нижний регистр.
2. Замена `ё` на `е`.
3. Выделение Unicode-последовательностей букв и цифр.
4. Исключение слов короче 3 символов.
5. Исключение фиксированного набора стоп-слов.
6. Использование первых 5 символов оставшихся слов как основы.

Пример:

```text
Исходное слово: ОБЛИГАЦИЯ
Нижний регистр: облигация
Основа: облиг
```

Нормализация используется только для поиска. Оригинальный текст цитат остаётся неизменным.

Список стоп-слов фиксирован в коде `STOP_WORDS` и не расширяется автоматически.

### Оценка совпадения

Для вопроса формируется множество уникальных основ.

Для каждого чанка вычисляются:

**Coverage** — доля уникальных основ вопроса, найденных в чанке.

```text
coverage = количество совпавших основ / количество основ вопроса
```

Кандидат проходит порог, если:

```text
coverage >= 0.6
```

**Match count** — количество вхождений основ вопроса в чанке с учётом повторений.

Повторения повышают `match_count`, но не увеличивают `coverage` сверх доли уникальных совпадений.

Если после нормализации вопроса не осталось поисковых основ, совпадений нет.

### Сортировка

Подходящие чанки сортируются по приоритетам:

1. `coverage` — по убыванию.
2. `match_count` — по убыванию.
3. `document.created_at` — новые документы первыми.
4. `document.id` — по возрастанию.
5. `block.position` — по возрастанию.
6. `chunk.position` — по возрастанию.

Выбираются максимум 3 чанка:

```text
TOP_K = 3
MIN_COVERAGE = 0.6
```

### Формирование цитат

Для выбранного чанка:

1. Находятся предложения и совпадения с основами вопроса.
2. Выбирается первое предложение с максимальным количеством совпадений.
3. Если предложение длиннее 300 символов, выбирается окно длиной 300 символов.
4. Вычисляется абсолютный диапазон цитаты.
5. Создаётся `Source` с UUID документа, блока и чанка.
6. Полностью одинаковые диапазоны одного документа исключаются.

Цитата берётся из исходного содержимого сохранённого блока и чанка.

Дополнительно проверяется согласованность содержимого чанка с его сохранённым диапазоном внутри блока.

## LLM-адаптер и MockLLM

В проекте сохранён интерфейс:

```python
LLMAdapter.generate(question: str, context: str) -> str
```

Фабрика `create_app()` позволяет внедрить альтернативный адаптер для тестов и дальнейшей интеграции.

### MockLLM

Текущая реализация находится в:

```text
app/llm/mock.py
```

`MockLLM` не обращается к внешнему сервису, не использует модель машинного обучения и не генерирует новые факты.

Его задача — детерминированно оформить реальные найденные цитаты.

Пример результата:

```text
[MOCK] Найдены фрагменты по ключевым словам вопроса:
1. «Облигация приносит доход.»
2. «Процентная ставка указана в условиях договора.»
```

Нумерация начинается с 1.

Если подходящих источников нет, `ChatService` сразу возвращает `insufficient_info` и не вызывает адаптер.

Если адаптер выбрасывает исключение, возвращает некорректный тип или становится недоступным, запрос получает ошибку `503 llm_unavailable`.

### Внедрение зависимостей

Фабрика приложения поддерживает:

```python
create_app(
    settings=...,
    llm_adapter=...,
    document_repository=...,
)
```

Это позволяет запускать тесты с временным файловым хранилищем и подменять LLM-адаптер без обращения к внешним сервисам.

## Восстановление после перезапуска

При запуске FastAPI через `lifespan` вызывается:

```python
repository.recover_incomplete()
```

Основные правила восстановления:

- `uploaded` → `error`.
- `processing` → `error`.
- `ready` остаётся `ready`, если результат доступен и корректен.
- `ready` → `error`, если `result.json` отсутствует или повреждён.
- `error` остаётся `error`.
- Незавершённые каталоги без `meta.json` удаляются.
- Повреждённые метаданные сохраняются для диагностики.

Для прерванной обработки используется код `processing_failed`.

Сообщение согласно контракту:

```text
Обработка была прервана перезапуском сервера. Загрузите файл ещё раз.
```

Ошибка восстановления одного документа не должна препятствовать восстановлению остальных.

Конструктор репозитория не запускает восстановление автоматически. Оно выполняется при старте приложения.

## Потоки и удаление

Для синхронизации файлового репозитория используется `threading.RLock`.

Блокировка защищает создание, изменение статусов, сохранение результатов, удаление и восстановление.

Во время длительной операции `process_txt()` блокировка не удерживается.

Если документ удалён во время обработки, последующее сохранение результата не должно создавать его заново.

Backend 0.6 рассчитан на один процесс Uvicorn.

Межпроцессная синхронизация и работа нескольких worker-процессов с общим файловым каталогом не поддерживаются.

## Обработка TXT

Модуль `app/processing/` реализует:

- Декодирование UTF-8 и UTF-8 BOM.
- Проверку пустого содержимого и некорректной кодировки.
- Сохранение пробелов и переносов строк.
- Создание блоков документа.
- Разбиение текста на чанки по 350 токенов с перекрытием 50 токенов.
- Сохранение точных символьных диапазонов.
- Детерминированные UUID5 для блоков и чанков.

Пример прямого вызова:

```python
from uuid import uuid4

from app.processing import process_txt

result = process_txt(
    "Привет, FinDocs!".encode("utf-8"),
    uuid4(),
)

print(result.blocks)
print(result.chunks)
```

`process_txt()` обрабатывает исходные данные в памяти.

Сохранение оригиналов, метаданных и результатов выполняется через `DocumentRepository`.

Backend 0.6 использует созданные ранее чанки. Новый запрос `/chat/ask` не запускает повторную обработку TXT.

## Ручная сквозная проверка

После запуска сервера создайте документ:

```bash
printf 'Облигация приносит процентный доход.\n' > example.txt
```

Загрузите TXT:

```bash
curl -i \
  -F "file=@example.txt;type=text/plain" \
  http://127.0.0.1:8000/documents
```

Скопируйте `id` из ответа и получите статус:

```bash
curl http://127.0.0.1:8000/documents/<uuid>
```

Замените `<uuid>` на реальный идентификатор документа.

Дождитесь статуса `ready`.

Задайте вопрос:

```bash
curl -X POST http://127.0.0.1:8000/chat/ask \
  -H "Content-Type: application/json" \
  -d '{
    "question": "облигация процентный доход"
  }'
```

Ожидаемое поведение:

- HTTP `200 OK`.
- `status: "answered"`.
- Текст ответа начинается с `[MOCK]`.
- `sources` содержит хотя бы один источник.
- У каждого источника есть реальные `document_id`, `block_id` и `chunk_id`.
- `quote` совпадает с соответствующим срезом исходного TXT.

Вопрос, для которого нет лексических совпадений, должен возвращать `insufficient_info` с пустым массивом источников.

## Интеграция с frontend

Для локальной разработки с React/Vite используется **Vite dev proxy**.

Frontend отправляет запросы через прокси Vite, который перенаправляет их на FastAPI по адресу:

```text
http://127.0.0.1:8000
```

Типовой сценарий:

1. Пользователь выбирает TXT.
2. Frontend вызывает `POST /documents`.
3. Backend сохраняет файл и возвращает `202`.
4. Frontend периодически вызывает `GET /documents/{document_id}`.
5. При статусе `ready` документ становится доступным для поиска.
6. Пользователь вводит вопрос.
7. Frontend вызывает `POST /chat/ask`.
8. Backend возвращает `answer`, `status` и `sources`.
9. Frontend отображает ответ и ссылки на исходные документы.

Для вопросов без выбранных документов frontend может отправлять `document_ids: null`.

Для вопросов по конкретным документам нужно передавать массив их UUID.

Конкретная конфигурация proxy находится на стороне frontend.

Vite dev proxy предназначен для локальной разработки и не заменяет настройку сетевого взаимодействия при развёртывании.

## Ограничения Backend 0.6

Текущий этап — демонстрационный MVP.

В него не входят:

- Настоящая LLM и генерация ответов моделью.
- Семантический поиск.
- Embeddings.
- Векторные индексы и pgvector.
- PostgreSQL.
- Ollama и внешние LLM API.
- PDF, DOCX и OCR.
- Авторизация пользователей.
- История диалогов и сохранение сессий.
- Оценка фактической достоверности сгенерированных выводов.
- Семантическая проверка цитат.
- Несколько процессов Uvicorn с общим файловым хранилищем.

Лексический поиск работает по совпадениям нормализованных слов. Он не понимает синонимы, скрытый смысл и сложные перефразирования.

Статус `answered` означает, что найдены подходящие по алгоритму фрагменты и сформирован демонстрационный ответ. Он не является гарантией правильного ответа на финансовый вопрос.

`MockLLM` не даёт финансовых рекомендаций и не заменяет настоящую языковую модель.

Backend 0.6 создаёт основу для будущей интеграции полноценного RAG, embeddings и LLM.
