## 2. Матрица прав

Действие (`x-rbac-action` в `openapi.yaml`) × роль. `+` — разрешено. `–` — `403 forbidden` (участнику ресурс известен). Не участнику пространства — всегда `404`. Ограничения по состоянию пространства — `mvp2.0_contracts.md` §9.

| Действие | Операции | viewer | editor | owner |
|---|---|:-:|:-:|:-:|
| `workspace.read` | GET пространства | + | + | + |
| `workspace.rename` | PATCH | – | – | + |
| `workspace.archive` | archive / unarchive | – | – | + |
| `workspace.delete` / `workspace.restore` | DELETE / restore | – | – | + |
| `workspace.transfer` | передача владения (с паролем) | – | – | + |
| `member.list` | список участников | + | + | + |
| `member.change_role` / `member.remove` | смена роли / исключение | – | – | + |
| `member.leave` | выход | + | + | – (сначала передать) |
| `invitation.manage` | создать / список / отозвать | – | – | + |
| `folder.read` | список папок | + | + | + |
| `folder.write` | создать / изменить / переместить / удалить пустую | – | + | + |
| `document.read` | список, метаданные, скачивание оригинала | + | + | + |
| `document.write` | загрузка; переименование, перенос, переобработка **любых** документов пространства | – | + | + |
| `document.delete` | удаление документа | – | только загруженных им (`uploaded_by` = я) | любых |
| `chat.own` | создать, читать, переименовать, архивировать, удалить **свой** чат | + | + | + |
| `chat.ask` | вопрос в своём чате (решение №1: viewer задаёт вопросы) | + | + | + |
| чужой чат | любое действие | 404 | 404 | 404 (владелец пространства тоже не видит чужие чаты) |
| `search.diagnostics` | диагностический поиск (только при флаге, не в `stand`) | – | + | + |

**Реализация.** Словарь `ACTION → min_role` в `workspaces/access.py`. Зависимость FastAPI `require_access(action)` извлекает `workspace_id` из пути, загружает членство и состояние пространства, возвращает `AccessContext`. Параметризованный тест WS-08 проходит по всем действиям × {viewer, editor, owner, не-участник, участник архивного пространства, участник удаляемого}. Тест-«сторож» SEC-13 проверяет, что каждый маршрут с `{workspace_id}` объявляет `x-rbac-action` и вызывает `require_access`.

**Удаление документов editor без обхода** (решение №1, требование №5):

| Возможный обход | Почему невозможен |
|---|---|
| Удалить чужой документ напрямую | сервис: `document.delete` + проверка `uploaded_by`; БД: триггер `documents_delete_guard` (`document_delete_forbidden`) |
| Удалить папку вместе с чужими документами | удаляется только пустая папка (сервис + FK `RESTRICT`); каскадного удаления содержимого нет |
| Присвоить себе документ и затем удалить | `uploaded_by` неизменяем (триггер `document_uploader_immutable`); в API поля нет |
| Перенести документ в другое пространство и удалить там | перенос между пространствами не реализован; составной FK и RLS не дают сменить `workspace_id` |
| Удалить пространство | только owner |
| Перезаписать документ переобработкой | переобработка не удаляет оригинал; при неудаче остаётся прежняя версия |
| Документ автора, удалившего аккаунт | автор остаётся ссылкой на обезличенную запись, поэтому удалить такой документ может только owner |

Проверки — SQL-тест `45_delete_policy.sql` и DEL-01…06.

**Политика 403/404:** ресурс в пространстве, где пользователь не участник, или чужой чат → `404 <resource>_not_found`. Ответ неотличим от несуществующего UUID по телу и заголовкам. Время ответа выравнивается по возможности, без гарантии. Участнику с недостаточной ролью → `403 forbidden` с `details.required_role`.

## 3. Аутентификация и восстановление доступа

### 3.1. Регистрация

Решение №3: **открытая самостоятельная регистрация** без участия администратора (`FINDOCS_REGISTRATION_MODE=open` по умолчанию). Режим `closed` остаётся конфигурационной опцией (`403 registration_closed`).

- Гостевой `POST /api/v1/auth/register` защищён проверкой `Origin` (§3.5) и throttle: 5 регистраций в час на IP-префикс (§3.7). Действует лимит `FINDOCS_MAX_USERS` (по умолчанию 50) — страховка на случай, если окружение случайно окажется доступным извне.
- В одной транзакции создаются пользователь, личное пространство, сессия и **код восстановления** (§3.2). Код показывается один раз; frontend требует подтвердить, что он сохранён.
- SMTP не подключается, email не подтверждается. Это известные ограничения закрытого тестирования: email — только идентификатор входа, владение почтой не доказано. Ответ `409 email_taken` раскрывает факт регистрации email. Перед открытием сервиса внешним пользователям регистрация переходит на подтверждение email с одинаковым ответом «Проверьте почту» (решение №21).
- Открытая регистрация не означает публичной доступности: окружения работают локально или в командной сети (ARCH §3.3).

### 3.2. Восстановление пароля через администратора

Решение №3 требует процедуры, не основанной только на неподтверждённом email. Механизм — **код восстановления** (ADR-024, **approved**):

| Шаг | Что происходит |
|---|---|
| При регистрации | генерируется код: 20 символов из алфавита без похожих знаков, ≈100 бит. Пользователь видит его один раз, в БД хранится только `SHA-256` (`users.recovery_code_hash`) |
| Пользователь забыл пароль | обращается к администратору по каналу команды и называет email. Код по возможности не пишется в переписку: пользователь продиктовывает его во время звонка или вводит сам на машине администратора (см. ниже). Если код всё же прислан сообщением, сообщение удаляется после сброса; код в любом случае перестаёт действовать после сброса |
| Администратор | `python -m app.admin reset-password --email …`. **Код не передаётся через аргументы командной строки, переменные окружения или файлы:** они видны в списке процессов (`ps`), истории оболочки и журналах. Команда запрашивает код интерактивно через скрытый ввод (`getpass`, без эха); при запуске без терминала она завершается с ошибкой. Для автотестов есть единственный вариант — чтение из стандартного ввода с явным флагом `--recovery-code-stdin`, запрещённым при `FINDOCS_ENV=stand`. Код не пишется в логи и аудит, хранится в памяти только до сравнения хэша. Не больше 5 неверных попыток на аккаунт в сутки, затем блокировка и аудит. При совпадении выпускается одноразовая ссылка `/set-password#token=…` (30 мин), ссылка передаётся пользователю |
| Пользователь | задаёт новый пароль; все сессии отзываются; выдаётся **новый** код восстановления, старый перестаёт действовать |
| Смена кода по желанию | `POST /api/v1/auth/recovery-code` с подтверждением пароля |

**Если код утерян — резервная процедура** (только для закрытого тестирования в команде). Сброс разрешён, **только если личность установлена достоверно**. Это значит, что выполнены все три условия:

1. Пользователь лично известен участнику команды и подтвердил запрос в рабочем канале команды из своей учётной записи в этом канале, существовавшей до запроса.
2. Пользователь назвал не меньше двух сведений об аккаунте, которые не видны посторонним и не выводятся из email: названия его общих пространств, имена недавно загруженных документов, примерную дату регистрации. Администратор сверяет их в admin-CLI, сами ответы не записываются.
3. Сброс одобрил второй участник команды, не администратор, выполняющий сброс (принцип двух лиц).

**Если хотя бы одно условие не выполнено или есть сомнения — сброс запрещён.** Администратор отказывает. Событие `auth.reset_refused` пишется в аудит без причин и персональных сведений. Обходных путей нет: ручное изменение `password_hash` в БД, выпуск токена без процедуры, «временный» пароль запрещены и считаются инцидентом ИБ.

Последствия отказа:

- аккаунт остаётся недоступным;
- пользователь может зарегистрировать новый аккаунт, а владельцы общих пространств — пригласить его снова;
- документы в общих пространствах остаются доступны другим участникам по их ролям;
- если он был единственным владельцем общего пространства, передать владение нельзя — известное ограничение закрытого тестирования, данные пространства доступны остальным участникам.

Успешная резервная процедура пишет `auth.reset_fallback` с указанием обоих участников. Перед открытием сервиса вовне резервная процедура заменяется восстановлением по подтверждённому email.

Общие правила токена сброса:

- выпуск нового токена отзывает предыдущий в той же транзакции;
- потребление атомарно, ответ одинаков для несуществующего, истёкшего, отозванного и использованного токена (`400 invalid_or_expired_token`);
- токен хранится как SHA-256 и передаётся **во фрагменте** URL (`#token=`), поэтому не попадает в журналы и `Referer`;
- восстановление по одному знанию email запрещено.

### 3.3. Пароли

- Длина 15–128 символов, требований к составу нет. Запрещены пароли из локального списка скомпрометированных и ожидаемых (топ-100 тыс. утечек + «findocs», название окружения, email, его локальная часть, имя пользователя) → `422 weak_password`.
- Ориентир — NIST SP 800-63B-4 («Password Verifiers»): при аутентификации только паролем минимум 15 символов. Это ориентир, а не обязательный для проекта стандарт. Проверка вхождения email и имени — продуктовая политика (снижает предсказуемость), её можно отключить решением Максима.
- Хэш argon2id (`argon2-cffi`): `memory_cost=19456` КиБ, `time_cost=2`, `parallelism=1`. Если параметры устарели, при успешном входе хэш пересчитывается.
- Семафор `FINDOCS_ARGON2_MAX_CONCURRENCY` (2) в процессе API. API работает одним процессом uvicorn, поэтому семафор глобален. Хэширование выполняется в пуле потоков и не блокирует цикл событий. Если ожидание семафора дольше 5 с → `429`.

### 3.4. Сессии

- Токен: 32 случайных байта, в cookie `__Host-findocs_session` (HttpOnly, Secure, SameSite=Lax, Path=/). В БД — только SHA-256.
- Сроки (решение №3): простой 12 ч, абсолютный срок 7 дней. `last_seen_at` и `idle_expires_at` обновляются не чаще раза в 5 минут.
- Каждый вход создаёт новую сессию, а сессия из входящей cookie, если она есть, отзывается (защита от фиксации сессии). Не больше 50 активных сессий на пользователя.
- Смена пароля отзывает все сессии, кроме текущей. Сброс пароля, отключение и удаление пользователя отзывают все.
- Обязательная проверка `users.status = 'active'` при каждом запросе: отключение действует сразу.

### 3.5. CSRF

Классы маршрутов и проверки — `mvp2.0_contracts.md` §2.2. Коротко:

- **Гостевые POST** (`login`, `register`, `password/set`): строгая проверка `Origin` по `FINDOCS_ALLOWED_ORIGINS` + `Sec-Fetch-Site: same-origin`, если заголовок есть. Хэш CSRF в отсутствующей сессии не требуется. Login CSRF закрыт проверкой `Origin`.
- **Аутентифицированные изменяющие:** `Origin` **и** `X-CSRF-Token`, совпадающий с `csrf_token_hash` сессии. Нет `Origin` → `403 origin_not_allowed`. Клиенты без браузера (QA-скрипты) обязаны передавать `Origin`.
- CSRF-токен выпускается при входе и регистрации, меняется при каждом входе, живёт столько же, сколько сессия.
- Разрешённые origin в `dev`: `http://localhost:5173`, `http://127.0.0.1:5173`. В `stand`: ровно один `https://` origin окружения.

### 3.6. Приглашения в пространство

- Только для общих пространств и только для **существующих** пользователей. Владелец создаёт ссылку `https://<origin>/invite#token=…` (TTL ≤ 7 дней, роль `editor` или `viewer`), токен показывается один раз.
- Приглашённый открывает ссылку. Если он не вошёл, frontend сохраняет токен в `sessionStorage`, ведёт на вход и после входа возвращается на `/invite`. Затем `POST /api/v1/invitations/lookup {token}` возвращает только имя пространства, роль и срок; `POST /invitations/accept {token}` принимает приглашение.
- Принятие атомарно (`app_accept_invitation`): блокировка строки приглашения, проверка `pending`, срока, состояния пространства (`active`, `shared`), отсутствия членства. Роль берётся из приглашения, из запроса она не принимается. Повтор → `404`, уже участник → `409 already_member`.
- Throttle: 20 попыток lookup или accept в час на пользователя и IP-префикс.

### 3.7. Throttle

Ключи и окна:

| Ключ | Лимит | Последствие |
|---|---|---|
| `login:pair:<sha256(email)>:<ip_prefix>` | 5 неудач / 15 мин | блок пары на 15 мин (`429` + `Retry-After`) |
| `login:email:<sha256(email)>` | 20 неудач / час | искусственная задержка 2 с на каждую следующую попытку, без полной блокировки (злоумышленник не может заблокировать жертву) |
| `register:ip:<prefix>` | 5 / час | `429` |
| `recovery:user:<id>` (CLI сброса по коду) | 5 неверных кодов / сутки | блокировка сброса по коду, аудит `auth.recovery_code_failed` |
| `token:ip:<prefix>` (`password/set`, приглашения) | 20 / час | `429` |

- Обновление — один атомарный `INSERT ... ON CONFLICT DO UPDATE` на ключ (эталон в `sql/tests/50_queries_jobs.sql`). Обе записи неудачного входа (пара и email) обновляются в одной транзакции. Перед проверкой пароля читается `max(locked_until)` по обоим ключам.
- IP-префикс: /24 для IPv4, /48 для IPv6. Адрес клиента берётся из `X-Forwarded-For` **только** если запрос пришёл от адреса из `FINDOCS_TRUSTED_PROXIES` (uvicorn `--proxy-headers --forwarded-allow-ips=<caddy>`); иначе используется адрес соединения.

## 4. Меры безопасности

### 4.1. Авторизация

§2. Плюс: репозитории не имеют методов «получить по id без `AccessContext`»; import-linter запрещает `api` обращаться к `repositories` напрямую.

### 4.2. RLS

ARCH §5.5: гарантии, границы гарантий, служебные роли, установка контекста и сброс в пуле. RLS включается вместе с таблицами, то есть с первой многопользовательской сборки. Что RLS не обеспечивает (роли внутри пространства, компрометацию роли приложения), обеспечивают сервис и тесты WS-08 и SEC-11.

### 4.3. Загрузки и файлы

Синхронные и асинхронные проверки — `mvp2.0_contracts.md` §8. Хранение — ARCH §6. Скачивание оригинала: `Content-Disposition: attachment`, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: sandbox`, `Cache-Control: private, no-store`. Предпросмотр PDF и DOCX — §4.5a (оригинал браузер сам не открывает: его читает PDF.js). Антивирусная проверка (ClamAV) — опция при открытии сервиса вовне.

### 4.4. Парсинг

ARCH §7.6, включая таблицу «что изоляция даёт и чего нет». Ограничение ресурсами — не песочница. Перед открытием сервиса внешним пользователям нужен отдельный контейнер-парсер без сети и секретов.

### 4.5. RAG и вывод модели

- ARCH §10.
- Frontend показывает ответ модели **как текст**: без `dangerouslySetInnerHTML` и без рендера Markdown в HTML. Если Markdown понадобится — санитайзер, запрет ссылок и изображений.
- Источники строятся только из `used_fragments`, прошедших серверную проверку.

### 4.5a. Предпросмотр документов

`mvp2.0_contracts.md` §11.4: PDF.js с отключённым исполнением JavaScript из PDF и `isEvalSupported: false`; worker PDF.js со своего origin; внешние ссылки только после подтверждения; текстовый режим — только текстовые узлы; оригинал по-прежнему `attachment` + `CSP: sandbox`; права и удаление проверяются при каждом запросе предпросмотра. CSP дополняется `worker-src 'self'`.

### 4.6. Транспорт и заголовки

TLS 1.2+ (Caddy), HSTS `max-age=31536000`. Для всех ответов:

```text
Content-Security-Policy: default-src 'self'; script-src 'self'; worker-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; connect-src 'self'; frame-ancestors 'none'; base-uri 'none'; form-action 'self'
X-Content-Type-Options: nosniff
Referrer-Policy: no-referrer
Permissions-Policy: camera=(), microphone=(), geolocation=()
Cross-Origin-Opener-Policy: same-origin
Cache-Control: no-store            # для /api/*
```

Сторонних ресурсов (CDN, шрифтов, аналитики) нет, иконки уже локальные. CORS выключен. `/docs` и `/openapi.json` FastAPI в `demo` отключены.

### 4.7. Секреты и конфигурация

Пароли ролей БД, `FINDOCS_CURSOR_SECRET`, ключ restic хранятся в Docker secrets или в `.env` вне git (`.gitignore` уже исключает `.env`). Проверки при старте в `stand`: нет `debug`, `legacy_single_user`, `mock`-провайдеров, режима регистрации `open`, http-origin, пустых секретов. Иначе процесс завершается с понятной ошибкой. gitleaks в CI.

### 4.8. Инфраструктура

Сети и роли процессов — ARCH §3.2, §13.4. Контейнеры запускаются от непривилегированного пользователя. Корневая ФС backend и worker — только для чтения, запись разрешена только в `blobs` и `/tmp`. Образы закреплены по digest и обновляются раз в месяц с прогоном CI. PostgreSQL и Ollama не публикуют порты. SSH к серверу — только по ключам, у администраторов пилота.

### 4.9. Логи и аудит (T-13)

**Что не пишется в логи никогда:** тексты документов и извлечённый текст; вопросы, ответы, цитаты; имена файлов (только `document_id`); email (только SHA-256); пароли; токены сессий, CSRF, сброса, приглашений; cookie; заголовки `Authorization`, `Cookie`, `X-CSRF-Token`; тела запросов и ответов.

Меры:

- Логируется **шаблон маршрута** (`/api/v1/workspaces/{workspace_id}/documents/{document_id}`), а не сырой путь. Строки запроса не логируются вовсе.
- Журнал доступа Caddy: формат `filter` — удаление `request>uri` query, `request>headers>Cookie`, `request>headers>X-Csrf-Token`, `resp_headers>Set-Cookie`. Токенов в путях нет по построению (фрагменты и тела).
- Журнал доступа uvicorn отключён, его заменяет middleware приложения с шаблоном маршрута.
- SQLAlchemy: `echo=False`, `hide_parameters=True`. Ошибки БД логируются кодом SQLSTATE и именем ограничения, без параметров.
- Исключения парсеров перехватываются в дочернем процессе. Родитель получает только код ошибки. Текст исключения, который может содержать фрагменты документа, не логируется.
- Тест SEC-15: сквозной сценарий с уникальной строкой в документе, вопросе, имени файла и токене. Затем поиск этих строк во всех журналах контейнеров — их там быть не должно.

**Аудит (`audit_events`):**

| action | meta (белый список полей) |
|---|---|
| `auth.login`, `auth.login_failed`, `auth.logout`, `auth.password_changed`, `auth.registered`, `auth.reset_issued`, `auth.token_consumed`, `auth.recovery_code_regenerated` | `reason` (для отказов), `operator` (для CLI) |
| `workspace.created`, `.renamed`, `.archived`, `.deleted`, `.restored`, `.purged`, `.ownership_transferred` | `new_owner_id` |
| `member.added`, `.role_changed`, `.removed`, `.left` | `user_id`, `role` |
| `invitation.created`, `.revoked`, `.accepted` | `role` |
| `document.uploaded`, `.deleted`, `.downloaded`, `.reprocessed` | `format`, `size_bytes` |
| `access.denied` | `action`, `status` (403/404) |
| `auth.reset_fallback`, `auth.reset_refused`, `auth.recovery_code_failed` | `operators` (для резервной процедуры); без причин отказа и ответов пользователя |
| `admin.reindex`, `admin.restore`, `admin.reapply_deletions` | счётчики |

- Запись аудита — в **той же транзакции**, что и действие. Если аудит не записался, действие откатывается. Исключение — `auth.login_failed` и `access.denied`: они пишутся в отдельной короткой транзакции, чтобы отказ не терялся при откате.
- У роли API только `INSERT`: она не читает, не меняет и не удаляет аудит. Чистит его sweeper под ролью worker по сроку 180 дней. Аудит доступен администратору через admin-CLI.
- Размер `meta` ограничен 2 КиБ (CHECK).

### 4.10. Удаление и сроки хранения

ARCH §5.6, §7.7 (sweeper), §13.5. Сроки: удалённые документы — purge сразу, файлы через 24 ч; superseded runs — 30 дней; сессии, токены и приглашения — 30 дней после истечения; аудит — 180 дней; бэкапы — до 35 дней. Удаление не распространяется на скачанные копии.

### 4.11. Персональные данные

Текущий режим (решения №21, №24) — локальная разработка и закрытое тестирование внутри команды. Документ **не утверждает соответствия** 152-ФЗ или иным требованиям. До открытия сервиса внешним пользователям отдельно решаются подтверждение email, обработка персональных данных, ИБ и готовность инфраструктуры. Технически схема поддерживает удаление и обезличивание пользователя (ARCH §5.6).

## 6. Протокол оценки поиска и генерации (T-10, T-11)

### 6.1. Набор данных

- Набор готовит Артём; объём согласовывается с его доступностью. Ориентир — 30 документов (TXT, PDF, DOCX; русский и смешанный текст; таблицы, числа, даты, аббревиатуры; длинные файлы) и 150 вопросов. Минимально допустимый объём для решения — 15 документов и 80 вопросов.
- Типы вопросов (доли фиксируются в манифесте набора): прямые; **перефразированные** (отдельная подвыборка); без ответа; на изоляцию scope; конфликтующие документы; по таблицам.
- **Разделение:** настроечная часть (≈ 40 %) — для подбора `TOP_K`, порогов и параметров RRF; **контрольная часть** (≈ 60 %) — только для финального сравнения. Разделение фиксируется в репозитории (`qa/eval/split.json`) **до** первого прогона гибрида и после этого не меняется.
- Вопросы MVP 1.0 (§7.2) входят как отдельная регрессионная группа, а не как доказательство улучшения.

### 6.2. Единица релевантности

Эталон — **якорь в извлечённом тексте**: документ + диапазон символов, в котором содержится ответ, размеченный по тексту run `pipeline_version` контрольного прогона. Найденный чанк релевантен, если пересекается с эталонным диапазоном хотя бы на 50 % длины меньшего из них. Так метрики не зависят от смены параметров чанкинга.

### 6.3. Метрики

| Метрика | Над чем | Примечание |
|---|---|---|
| Recall@k (k = 3, 5, 10) | вопросы с ответом | отдельно — по перефразированным |
| MRR, nDCG@5 | вопросы с ответом | — |
| Точность источников | ответы `answered` / `partial` | доля источников, пересекающих эталон |
| Доля ложных отказов | вопросы с ответом | `insufficient_info` при наличии эталона |
| Доля ложно уверенных ответов | вопросы без ответа | `answered` / `partial` без эталона |
| Корректность ответа | вопросы с ответом | обязательные факты из эталона присутствуют (проверка по списку фактов, без LLM-судьи) |
| Latency p50/p95 | retrieval и полный ответ | с указанием железа, модели, числа документов |
| Ресурсы | RAM/VRAM при совместной работе LLM и worker | замер на целевом сервере |

Вопросы без ответа в Recall@k не входят.

### 6.4. Решение

1. Сначала прогон baseline `lexical` на настроечной и контрольной частях.
2. **До** прогона кандидатов фиксируются пороги в `qa/eval/thresholds.md`, коммит с датой. Предлагаемая форма:
   - Recall@5 по перефразированным: прирост не меньше X п.п.;
   - Recall@5 по всем: не хуже baseline;
   - ложно уверенные ответы: не выше baseline + Y п.п.;
   - точность источников: не ниже Z;
   - p95 полного ответа: не выше W секунд на целевом железе.

   Значения X, Y, Z, W выбираются по результатам baseline и согласуются Максимом. Задним числом под победителя пороги не меняются.
3. Кандидаты (`fts`, `vector` с каждой моделью, `hybrid`) настраиваются только на настроечной части и сравниваются на контрольной.
4. Генерация недетерминирована даже при `temperature=0`. Поэтому каждый генерационный прогон повторяется 3 раза, в отчёт идёт медиана и разброс. Фиксируются модель, digest, железо и версия кода.
5. Если ни один кандидат не проходит пороги, остаётся `lexical` (или `fts`, если он не хуже), а отчёт фиксирует результат эксперимента без заявления об улучшении. ADR-029 принимается по этому отчёту.

### 6.5. Генерация

- Семантика `supported`, `used_fragments` и `partial` — ARCH §9.4. Флаг `partial` включается только после отдельного прогона: ложно уверенные `partial` не выше порога пункта 2.
- Проверка опоры (числа, даты, суммы) не доказывает правильность смысла. Утверждение «система не галлюцинирует» не делается. Делается измерение доли корректных ответов и ложно уверенных ответов.
- Prompt injection: mock-тесты проверяют **границы** (scope, права, источники только из переданных фрагментов). Реальные прогоны Ollama проверяют **поведение** модели на фикстурах. Ни то, ни другое не доказывает устойчивость к любой атаке.

Данные MVP 1.0 в 2.0 не переносятся (решение №9). Исторические результаты сохраняются и не перезаписываются, а сами материалы используются для регрессии: тестовые документы загружаются в MVP 2.0 как документы тестового пользователя и прогоняются по тем же вопросам.

Исторические «20/20» — результат конкретного прогона на конкретной модели. Это не гарантия качества на новых документах и не доказательство превосходства гибрида.

### 7.3. Независимая приёмка

| Чей код | Кто проверяет | Примечание |
|---|---|---|
| Максим (прикладной слой) | Артём и Влад | собственная проверка Максима не считается независимым QA |
| Артём (миграции, ограничения, репозитории, RLS, инфраструктура, бэкап) | **Влад и Максим совместно** (решение №20): архитектурное и техническое ревью | Артём не принимает свой код сам, даже как QA |
| Аня (frontend) | Максим (контракт), Артём (E2E) | — |
| Влад (контракты, SQL-эталон, ADR) | Максим и Артём | SQL-эталон Артём использует в работе и сообщает о расхождениях |
| Критичные изменения (auth, RLS, удаление, миграции, восстановление) | назначенный проверяющий, не автор | указывается в описании PR |

Каждый разработчик пишет тесты своего модуля. Матрица §5 ведётся отдельно от авторских тестов: QA проверяет по ней, а не по тестам автора.
